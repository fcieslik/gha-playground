# ADR-002: Deliver the static site through CloudFront with a private S3 origin

## Status

Accepted — 2026-07-29

## Context

The public S3 website endpoint proved the deploy loop but is not a
production boundary: it is HTTP-only and its public-read policy lets any
viewer read the bucket directly, bypassing any edge policy. We need one
public HTTPS entry point while keeping the tested `site` artifact and the
existing least-privilege deploy identity from lesson 7. Edge caching lowers
latency and origin load, but makes a new or rolled-back object temporarily
less immediately visible.

## Decision

We will serve the site through a CloudFront distribution with an S3 REST
origin (not the S3 website endpoint), Viewer protocol set to redirect HTTP
to HTTPS, and an Origin Access Control that always signs origin requests.
The bucket keeps Block Public Access on and allows `s3:GetObject` only to
the `cloudfront.amazonaws.com` service principal when `AWS:SourceArn` equals
this distribution's ARN. The default root object is `index.html`.

## Consequences

- Direct S3 object URLs return 403 AccessDenied; the CloudFront domain is
  the only public delivery entry point. The deploy job keeps its separate
  `PutObject`/`DeleteObject` authority and gains no CloudFront write access.
- Cache/freshness: we accept propagation and caching delay. A release or
  rollback needs a `/*` invalidation to become visible promptly, until
  content-hashed asset names make long immutable caching safe (deferred).
- Rollback: re-syncing an older artifact is not enough on its own — edge
  caches may still serve the newer object, so a rollback must also invalidate
  before the restored release is actually visible.
- CloudFront adds a billable service and a second operational configuration
  that can fail independently of the S3 sync.
