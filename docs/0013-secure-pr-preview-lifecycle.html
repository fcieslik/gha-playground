Secure PR Preview Lifecycle

Lesson 13 · planned lesson 17 · ~60–90 min · build untrusted code without credentials, publish one isolated preview through a dev-only role, then remove it on close

Prerequisite: lesson 12 complete: production uses an approved OIDC role, the static AWS keys are gone, and the separate dev Environment exists.

A preview is a temporary deployment with a lifecycle: a successful same-repository PR build creates or replaces previews/pr-<number>/; closing that PR removes exactly the same prefix. The difficult part is not aws s3 sync. It is preventing code under review from controlling the job that receives AWS credentials.

untrusted pull_request run trusted default-branch run ┌─────────────────────────────┐ ┌──────────────────────────────┐ │ checkout PR merge commit │ │ workflow_run after green CI │ │ npm ci + test + build │── site ──► │ approve dev Environment │ │ upload artifact │ artifact │ assume dev-only OIDC role │ │ no id-token, no AWS │ │ sync bytes; execute nothing │ └─────────────────────────────┘ └──────────────┬───────────────┘ ▼ s3://DEV/previews/pr-42/ │ PR closed → unprivileged cleanup request → trusted workflow_run → delete pr-42/

The first workflow may execute hostile code, so it receives no cloud identity. The second workflow may receive a dev identity, so it never checks out the PR or executes its artifact. GitHub documents workflow_run as a privilege-separation mechanism, but also warns that its artifacts are untrusted; this design uses the artifact only as static files to upload.

Continue Frontend Masters’ Cloud CI/CD with GitHub Actions by applying its Environment Protection & OIDC boundary to a pre-production target. GitHub’s current workflow_run reference and secure-use guidance are authoritative for the cross-run handoff and untrusted-artifact rule. Keep the PR preview lifecycle reference open.

Checkpoint 1 — give previews their own blast radius

Create a separate private preview bucket and CloudFront distribution by repeating the S3 REST origin + OAC pattern from lesson 11. Use a separate dev hostname or CloudFront domain; preview HTML is reviewer-visible but still attacker-controlled, so it must not inherit production cookies, credentials, or origin trust.

For this learning project, attach CloudFront’s managed CachingDisabled policy to the dev distribution. Its minimum, default, and maximum TTL are all zero, so replacing or deleting a preview is observable immediately. Lesson 14 will make the production latency–cost–freshness decision explicitly; do not weaken production caching today.

Now tighten the dev Environment from lesson 12:

  • add a required reviewer; allow self-review only if solo practice makes separation of duties impossible;
  • store AWS_ACCOUNT_ID, AWS_REGION, AWS_ROLE_ARN, DEV_S3_BUCKET, and DEV_BASE_URL as environment variables;
  • create gha-dev-preview with the exact immutable OIDC subject ending in environment:dev;
  • grant it access only to previews/* in the dev bucket—no production bucket and no production distribution. 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "LocatePreviewBucket",
      "Effect": "Allow",
      "Action": "s3:GetBucketLocation",
      "Resource": "arn:aws:s3:::DEV_BUCKET"
    },
    {
      "Sid": "ListOnlyPreviewPrefixes",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::DEV_BUCKET",
      "Condition": {
        "StringLike": {
          "s3:prefix": ["previews/*"]
        }
      }
    },
    {
      "Sid": "ManageOnlyPreviewObjects",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::DEV_BUCKET/previews/*"
    }
  ]
}

S3 has objects and key prefixes, not real directories. The bucket-level ListBucket permission therefore uses an s3:prefix condition, while object writes and deletes use the narrower object ARN. The role can replace any preview, but cannot escape the dev bucket or reach production.

Checkpoint 2 — keep PR CI unprivileged

Give the event-facing workflow a stable display name because workflow_run.workflows matches it. Keep its existing PR CI and post-merge production deploy; do not add id-token: write to the caller or reusable CI. 

name: Pipeline

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  ci:
    name: ci
    uses: ./.github/workflows/ci.yml

  deploy:
    if: github.event_name == 'push'
    needs: ci
    # existing production Environment + OIDC deploy remains unchanged

On a fork PR, GitHub withholds secrets and reduces GITHUB_TOKEN to read-only. OIDC is not a stored secret, however, so “forks receive no secrets” is not a sufficient cloud boundary. The privileged workflow below also requires head_repository.full_name == github.repository; fork builds remain useful CI, but cannot reach the dev Environment.

Add one inert close-event workflow. It carries no credentials and checks out nothing; it exists only to produce a completed run that the trusted lifecycle workflow can observe. 

# .github/workflows/preview-cleanup-request.yml
name: Preview cleanup request

on:
  pull_request:
    branches: [main]
    types: [closed]

permissions: {}

jobs:
  request:
    runs-on: ubuntu-latest
    steps:
      - name: Record lifecycle event
        env:
          PR_NUMBER: ${{ github.event.number }}
        run: echo "Preview cleanup requested for PR $PR_NUMBER"

Do not switch to pull_request_target and check out the PR. That event runs in the base repository’s privileged context. GitHub’s secure-use guidance warns that combining privileged triggers with untrusted checkout can expose write tokens or secrets.

Checkpoint 3 — publish from the trusted side

Create .github/workflows/preview-lifecycle.yml on main. It responds to completed runs of either named workflow. workflow_run loads this definition from the default branch, so a PR cannot edit the privileged steps it is about to trigger. 

name: Preview lifecycle

on:
  workflow_run:
    workflows: [Pipeline, Preview cleanup request]
    types: [completed]

permissions: {}

jobs:
  deploy:
    if: >-
      github.event.workflow_run.name == 'Pipeline' &&
      github.event.workflow_run.event == 'pull_request' &&
      github.event.workflow_run.conclusion == 'success' &&
      github.event.workflow_run.head_repository.full_name == github.repository &&
      github.event.workflow_run.pull_requests[0].number != null
    runs-on: ubuntu-latest
    environment:
      name: dev
      url: ${{ vars.DEV_BASE_URL }}/previews/pr-${{ github.event.workflow_run.pull_requests[0].number }}/index.html
    permissions:
      actions: read
      contents: read
      id-token: write
    env:
      DEV_BUCKET: ${{ vars.DEV_S3_BUCKET }}
      DEV_BASE_URL: ${{ vars.DEV_BASE_URL }}
      PREVIEW_NUMBER: ${{ github.event.workflow_run.pull_requests[0].number }}
    steps:
      - name: Derive a safe preview target
        shell: bash
        run: |
          [[ "$PREVIEW_NUMBER" =~ ^[1-9][0-9]*$ ]]
          echo "PREVIEW_PREFIX=previews/pr-$PREVIEW_NUMBER" >> "$GITHUB_ENV"
          echo "PREVIEW_URL=${DEV_BASE_URL%/}/previews/pr-$PREVIEW_NUMBER/index.html" >> "$GITHUB_ENV"

      - name: Download the successful CI artifact
        uses: actions/download-artifact@v8
        with:
          name: site
          path: ${{ runner.temp }}/site
          run-id: ${{ github.event.workflow_run.id }}
          github-token: ${{ github.token }}

      - name: Validate artifact as data
        run: |
          test -f "$RUNNER_TEMP/site/index.html"
          grep -F "Deployed by GitHub Actions" "$RUNNER_TEMP/site/index.html"

      - name: Configure temporary dev credentials
        uses: aws-actions/configure-aws-credentials@v6.2.3
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}
          aws-region: ${{ vars.AWS_REGION }}
          allowed-account-ids: ${{ vars.AWS_ACCOUNT_ID }}
          role-session-name: preview-${{ github.run_id }}-${{ github.run_attempt }}

      - name: Replace only this PR preview
        run: aws s3 sync "$RUNNER_TEMP/site/" "s3://$DEV_BUCKET/$PREVIEW_PREFIX/" --delete

      - name: Verify the preview
        run: |
          curl --fail --retry 8 --retry-delay 2 "$PREVIEW_URL" |
            grep -F "Deployed by GitHub Actions"

Notice what is absent: no checkout, no npm, no local action, and no shell script downloaded from the artifact. The trusted workflow interprets only a PR number from GitHub’s event payload, validates it as digits, and uploads already-built bytes to one prefix.

Exercise 1 — prove isolated create and update

Write the dev policy, cleanup-request workflow, and deploy job from scratch. Run actionlint. Merge these trusted workflow definitions to main before testing them; workflow_run only triggers from a definition present on the default branch.

Open a same-repository PR that changes visible site text. Confirm Pipeline finishes first, then Preview lifecycle pauses at dev. Inspect the PR and workflow changes before approval. Approve, visit the Environment URL, then push a second site change and approve again.

Both preview runs use assumed-role/gha-dev-preview/ and the same /previews/pr-N/index.html URL. The second run replaces that PR’s content. The production workflow, bucket, distribution, and role are untouched.
Failure routing
  • No lifecycle run: preview-lifecycle.yml is not yet on main, or workflows: [Pipeline] does not exactly match the triggering workflow’s name:.
  • Lifecycle run but deploy skipped: inspect conclusion, triggering event, head repository, and pull_requests[0].number in the event payload.
  • Artifact not found: pass both the triggering run-id and github-token; a plain download searches only the current run.
  • STS denied: the dev role trust subject must end in environment:dev, not a PR ref or production.
  • S3 denied: distinguish bucket-level listing from object-level write/delete resources.
  • Old content persists: confirm the dev distribution uses CachingDisabled; do not add production invalidation permissions to the dev role.

Checkpoint 4 — close means delete

Add a sibling cleanup job to preview-lifecycle.yml. It accepts only a successful Preview cleanup request run for a same-repository PR, assumes the same dev role, and deletes the validated prefix. Reuse the credential and prefix-derivation steps from deploy; then perform only this side effect and verification: 

  cleanup:
    if: >-
      github.event.workflow_run.name == 'Preview cleanup request' &&
      github.event.workflow_run.event == 'pull_request' &&
      github.event.workflow_run.conclusion == 'success' &&
      github.event.workflow_run.head_repository.full_name == github.repository &&
      github.event.workflow_run.pull_requests[0].number != null
    runs-on: ubuntu-latest
    environment: dev
    permissions:
      contents: read
      id-token: write
    env:
      DEV_BUCKET: ${{ vars.DEV_S3_BUCKET }}
      DEV_BASE_URL: ${{ vars.DEV_BASE_URL }}
      PREVIEW_NUMBER: ${{ github.event.workflow_run.pull_requests[0].number }}
    steps:
      # derive PREVIEW_PREFIX and PREVIEW_URL exactly as in deploy
      # configure the same gha-dev-preview role exactly as in deploy

      - name: Remove only this PR preview
        run: aws s3 rm "s3://$DEV_BUCKET/$PREVIEW_PREFIX/" --recursive

      - name: Prove the prefix is empty
        run: |
          KEY_COUNT="$(aws s3api list-objects-v2 \
            --bucket "$DEV_BUCKET" \
            --prefix "$PREVIEW_PREFIX/" \
            --query KeyCount \
            --output text)"
          test "$KEY_COUNT" = 0

      - name: Prove the URL is gone
        run: |
          STATUS="$(curl --silent --output /dev/null --write-out '%{http_code}' "$PREVIEW_URL")"
          test "$STATUS" = 403 -o "$STATUS" = 404

The aws s3 rm --recursive delete is safe only because the prefix is derived from a validated integer—not PR title, branch name, artifact text, or arbitrary input. Repeating cleanup is idempotent: zero matching objects remains success.

Exercise 2 — prove cleanup and fork denial
  1. Open two same-repository PRs and deploy both previews. Record their distinct URLs and list both S3 prefixes.
  2. Close one PR. Approve its cleanup, then verify its key count is zero and its URL returns 403 or 404.
  3. Verify the other PR preview still works. This is the isolation proof; “the target disappeared” alone is insufficient.
  4. From a fork, open a harmless PR. Let CI run, then inspect Preview lifecycle: the deploy job must be skipped by the head-repository condition, before any Environment approval or OIDC step.
Closing PR A removes only previews/pr-A/; PR B still serves its own content. The fork PR receives CI but produces no dev deployment, no approval prompt, and no AWS identity.
Self-check

Full credit requires four observations: two distinct live prefixes, one prefix empty after close, the sibling preview still live, and a fork-triggered deploy visibly skipped. Also confirm direct S3 reads remain denied and the production role’s policy contains no dev bucket ARN.

Check yourself

Design question — decide, then defend

Same-run convenience or cross-run privilege separation?

Choose (A) put id-token: write and preview deployment after CI in the PR’s own workflow run, or (B) let unprivileged PR CI finish and trigger a default-branch workflow_run deploy. Name the extra operational cost and the security consequence.

Model answer and rubric

Choose B. A PR can propose changes to its workflow. In the same-run design, approval may start privileged steps from that proposed definition; reviewers must notice every malicious workflow edit. The split keeps credential-bearing code on main and limits the handoff to an artifact that is validated and never executed.

The cost is a second workflow run, explicit cross-run artifact download, stable workflow-name coupling, harder event-context debugging, and a separate cleanup signal. Full credit requires a decision, at least one of those costs, and the rule that the privileged workflow never checks out or executes untrusted content.

Done means the lifecycle and its negative paths are proven. A green preview alone is incomplete: closing removes only its prefix, a sibling survives, a fork gets CI without deployment, and neither dev policy contains a production ARN nor production policy a dev ARN.

Ask your teacher if the downstream workflow does not trigger, the cross-run artifact is missing, the dev Environment never pauses, the role assumes but S3 denies one operation, cleanup removes the object but CloudFront still serves it, or a fork reaches an approval prompt. Bring both run URLs, the redacted event fields used by the job condition, the exact prefix, and the first failing AWS command.
