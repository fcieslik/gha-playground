Production Release Hardening

Lesson 14 · planned lesson 18 · ~90–120 min · make freshness, action code, and overlapping production releases deterministic

Prerequisite: lesson 12 complete: production is private behind CloudFront, requires Environment approval, and deploys through OIDC. Lesson 13’s previews may remain on their separate cache policy.

A green upload is not yet a trustworthy release. Users can still receive an old edge copy, a movable action tag can execute different code tomorrow, and two approved runs can mutate the same bucket at once. Today you will turn those three implicit risks into one explicit release contract.

immutable CI artifact │ ▼ production concurrency group ── one mutating deploy at a time │ ▼ approved production Environment ── OIDC role │ ├── upload HTML: revalidate on every request ├── upload fingerprinted assets: cache for one year ├── delete stale origin objects ├── invalidate /index.html and wait └── verify metadata + live content every remote action ── full commit SHA + readable release comment

The contract is deliberately asymmetric. A mutable entry point such as index.html must discover the current release quickly. An asset may be cached for a year only when its URL changes with its bytes, for example app.3f2a8c91.js. Concurrency then ensures that one complete artifact converges the origin before another release may start.

Watch Frontend Masters’ Pinning Workflows to SHAs and Managing Concurrency sections (04:04:47–04:18:01). GitHub’s current secure-use reference and concurrency reference are authoritative. For the delivery half, keep the production release contract open beside AWS’s cache-expiration guide.

Checkpoint 1 — classify URLs before setting TTLs

Class Example Policy Reason
Mutable entry point index.html public,max-age=0,s-maxage=0,must-revalidate The same URL may contain a new release.
Immutable asset assets/app.3f2a8c91.js public,max-age=31536000,immutable Changed bytes produce a changed URL.
Unfingerprinted asset assets/app.js Short TTL; never immutable The URL can lie about which bytes it names.

CloudFront and browsers are separate caches. AWS documents that s-maxage controls the shared CloudFront cache while max-age controls browsers, bounded by the cache behavior’s minimum and maximum TTL. Keep the production behavior on CachingOptimized; origin headers may shorten its default TTL, while fingerprinted assets retain the long policy.

A long TTL requires a content-derived filename. A version written by hand, a run number, or a date can still be reused accidentally. If the current build emits only index.html, apply only the HTML policy today. Add the immutable upload only after the build artifact contains fingerprinted paths.

Checkpoint 2 — upload metadata as part of the release

S3 stores Cache-Control as object metadata. A plain sync can skip unchanged files, so changing only the desired header does not necessarily rewrite existing metadata. Download the site artifact to ${{ runner.temp }}/site, use cp for the two policy classes, then use sync --delete to remove keys absent from the artifact. 

- name: Publish release with explicit cache metadata
  env:
    SITE_DIR: ${{ runner.temp }}/site
    PROD_BUCKET: ${{ vars.PROD_S3_BUCKET }}
  run: |
    set -euo pipefail

    aws s3 cp "$SITE_DIR/" "s3://$PROD_BUCKET/" \
      --recursive \
      --exclude "*" \
      --include "*.html" \
      --cache-control "public,max-age=0,s-maxage=0,must-revalidate"

    if test -d "$SITE_DIR/assets"; then
      if find "$SITE_DIR/assets" -type f |
        grep -Ev '/[^/]+\.[0-9a-f]{8,}\.[^/]+$'
      then
        echo "Every immutable asset needs a content hash in its filename" >&2
        exit 1
      fi

      aws s3 cp "$SITE_DIR/assets/" "s3://$PROD_BUCKET/assets/" \
        --recursive \
        --cache-control "public,max-age=31536000,immutable"
    fi

    aws s3 sync "$SITE_DIR/" "s3://$PROD_BUCKET/" --delete

The validation enforces the naming half of the artifact contract: files under assets/ must have at least eight lowercase hexadecimal characters between two dots. The build still owns proving that those characters come from the content. Adjust the check if your build tool emits a different proven content-hash format; do not delete it and keep the one-year TTL.

Then replace the blanket /* invalidation from lesson 11 with the only mutable viewer path. Wait for completion before claiming the release is live. 

- name: Revalidate the mutable entry point
  id: invalidate
  env:
    DISTRIBUTION_ID: ${{ vars.CLOUDFRONT_DISTRIBUTION_ID }}
  run: |
    set -euo pipefail
    invalidation_id="$(
      aws cloudfront create-invalidation \
        --distribution-id "$DISTRIBUTION_ID" \
        --paths "/index.html" \
        --query "Invalidation.Id" \
        --output text
    )"
    echo "id=$invalidation_id" >> "$GITHUB_OUTPUT"
    aws cloudfront wait invalidation-completed \
      --distribution-id "$DISTRIBUTION_ID" \
      --id "$invalidation_id"

With --paths, the AWS CLI generates the unique caller reference. A request for the distribution root returns the configured default root object, index.html, so invalidating that object covers the entry point. Immutable assets need no invalidation: a new release points at new URLs, while older HTML may continue to point at older assets until it revalidates.

Exercise 1 — prove the freshness contract

Write the publish and targeted-invalidation steps from scratch. If your artifact contains only HTML, omit the asset block but keep its rule in a comment. Run actionlint, merge a visible text change, approve production, and record the invalidation ID.

After the waiter completes, inspect both S3 metadata and the viewer response: 

aws s3api head-object \
  --bucket "$PROD_BUCKET" \
  --key index.html \
  --query CacheControl \
  --output text

curl --fail --silent --show-error --head \
  "$CLOUDFRONT_URL/index.html" |
  tr -d '\r' |
  grep -i '^cache-control:.*max-age=0'

curl --fail --silent --show-error "$CLOUDFRONT_URL/" |
  grep --fixed-strings "Deployed by GitHub Actions"
S3 and CloudFront both expose a zero-age policy for index.html; the targeted invalidation reaches Completed; the root URL contains the new release marker. No /* invalidation is created.
Solution and failure routing

The complete order is: download the existing site artifact, copy HTML with zero-age metadata, validate and copy any fingerprinted assets with immutable metadata, run sync --delete, create /index.html invalidation, wait for its ID, then verify metadata and live content.

  • Old metadata remains: the workflow still uses only sync; force the policy class through cp --cache-control.
  • CloudFront ignores zero age: inspect the behavior’s minimum TTL and whether it honors origin cache headers.
  • New origin, old viewer response: confirm the invalidation path is exactly /index.html and wait for its ID.
  • Asset validation fails: fingerprint the filename in the build; do not weaken the cache invariant.
  • Live check races: it must run after the invalidation waiter, not merely after the create request.

Checkpoint 3 — pin the code your credentials execute

A release tag such as @v7 is readable but movable. A full commit SHA is immutable and therefore the only action reference GitHub describes as immutable. Keep the release tag in a same-line comment so reviewers and Dependabot retain the human meaning. 

- uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7
- uses: actions/setup-node@820762786026740c76f36085b0efc47a31fe5020 # v7
- uses: actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a # v7
- uses: actions/download-artifact@3e5f45b2cfb9172054b4087a40e8e0b5a5461e7c # v8
- uses: aws-actions/configure-aws-credentials@e6de054238d6b7531b4efff3b6587d9aade6a06c # v6.2.3

These SHAs resolve the course versions on 29 July 2026. Before committing, independently resolve each reviewed tag with git ls-remote https://github.com/OWNER/REPO.git refs/tags/TAG. Pin every remote action in every workflow, including unprivileged CI: compromised build output later crosses into a credential-bearing deployment.

Add automated update proposals rather than trading immutability for staleness: 

# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly

Dependabot understands a SHA plus its same-line version comment. It opens a reviewable PR; green CI is evidence of compatibility, not permission to auto-merge code that will run beside deployment credentials.

Exercise 2 — make the action supply chain reviewable

Search .github/workflows and replace every remote tag with a verified 40-character commit SHA. Leave local actions and local reusable workflows as local paths. Add the Dependabot configuration, run actionlint, then enable the repository setting Require actions to be pinned to a full-length commit SHA if your plan exposes it. 

rg -n 'uses: [^./][^ ]+@(v|main|master)' .github/workflows
rg -n 'uses: [^./][^ ]+@[0-9a-f]{40}( |$)' .github/workflows
The first search returns nothing. The second lists every remote action with a full SHA. CI and the approved OIDC deployment remain green, and future action upgrades arrive as explicit reviewable diffs.
Solution and self-check

Use the five resolved SHAs above with their same-line release comments, then configure weekly github-actions Dependabot updates. Do not pin to a shortened SHA, a release tag, or a branch. Confirm that each SHA belongs to the intended upstream repository and release. Full credit also requires an update path: Dependabot or an equivalent reviewed process.

Checkpoint 4 — serialize the production mutation

Add concurrency to the deploy job, not the whole workflow. PR CI and build jobs may remain parallel; only jobs mutating the shared production bucket and distribution need the lock. 

deploy:
  if: github.event_name == 'push'
  needs: ci
  runs-on: ubuntu-latest
  environment:
    name: production
    url: ${{ vars.CLOUDFRONT_URL }}
  concurrency:
    group: production-deploy
    cancel-in-progress: false
  permissions:
    contents: read
    id-token: write
  steps:
    # pinned actions → publish → invalidate and wait → verify

environment and concurrency are independent controls. The Environment decides whether a release may start and exposes the OIDC subject; the static concurrency group ensures only one production mutation runs at a time—even if a second workflow later deploys to the same target and uses the same group.

With the default single pending slot, a third release replaces an older pending release while the current release finishes. That is correct for this full-state static-site deployment: the newest artifact subsumes an intermediate artifact. If every release carries a non-skippable migration or audit step, use GitHub’s current queue: max mode or, preferably, separate that ordered operation from a replaceable site deploy.

Exercise 3 — force and observe an overlap

Temporarily add sleep 60 immediately before the publish step. Prepare two already-green PRs with different visible release markers. Merge A, approve its production job, and wait until it reaches the sleep. Then merge B.

Inspect both runs before approving anything else. B’s deploy must wait on production-deploy; it must not assume the role or touch S3 while A owns the group. Let A finish, approve B when it becomes eligible, and then remove the temporary sleep through the normal PR path.

At no moment do two jobs execute production AWS commands. A completes its upload, invalidation, waiter, and verification before B begins them. The final URL contains B’s marker, and the workflow history preserves both release outcomes.
Solution and failure routing

Both deploy jobs use the exact static group production-deploy with cancel-in-progress: false. A runs every mutating step to completion; only then may B enter the same job and publish the newer full-state artifact.

  • Both deploys run: their group strings differ, or concurrency was attached to a different job.
  • The older run is canceled mid-upload: cancel-in-progress is true; production mutation must finish.
  • All CI waits: concurrency was placed at workflow level instead of on the deploy job.
  • B publishes before A: inspect whether another workflow targets production without the shared group.

Check yourself

Design question — decide, then defend

Invalidate everything or version the expensive paths?

Choose (A) keep stable asset names and invalidate /* on every release, or (B) use content-hashed asset names, revalidate only HTML, and invalidate /index.html. Name the operational cost and the freshness consequence of your choice.

Model answer and rubric

Choose B. Immutable asset URLs let browsers and edges cache aggressively without serving incorrect bytes for that URL. The mutable HTML entry point gets zero-age metadata plus a targeted invalidation, so it discovers the new asset graph promptly. Rollback republishes older HTML and invalidates the same entry point; its older hashed assets may safely remain cached.

The cost is a stricter build contract: filenames must be content-derived, HTML references must change with them, and old assets need a deliberate retention or cleanup policy. Full credit requires a decision, that build/retention cost, and the distinction between origin convergence, edge invalidation, and browser cache behavior.

Done means you have negative evidence, not only one green run. Show that no remote action tag remains, an unfingerprinted immutable asset fails validation, two production deploys cannot overlap, the invalidation reaches Completed, and the final live marker belongs to the newest release.

Ask your teacher if metadata changes do not reach S3, CloudFront still serves old HTML after a completed invalidation, the SHA policy rejects a local action, Dependabot loses the readable version, or two production jobs overlap.
