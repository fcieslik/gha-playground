Reusable & Enforced CI

Combined lessons 10–12 · ~90–120 min · reuse one step, reuse the CI graph, then make its stable result a merge requirement

Prerequisite: lesson 9 complete and a green pipeline.yml: PRs build/test, post-merge pushes build/test/deploy, the site artifact reaches S3, and both Node setup steps use the npm cache without skipping npm ci.

Your pipeline works, but its structure is still only a convention. The deploy summary is shell code embedded in one job; the complete CI contract is embedded in one event-facing workflow; and GitHub still lets a human merge while CI is red. You will strengthen those three seams in order: package a repeated step as a composite action, package the jobs as a reusable workflow, then make one stable result a repository rule.

This is one longer session because the pieces explain one another. Reuse without enforcement is optional convention. Enforcement against unstable matrix names is brittle. A stable gate without real jobs behind it is theatre. The completed path is:

Choose the reuse boundary by what must move

NeedSmallest fitting toolInvocation boundary
A few repeated commands inside a jobComposite actionA step: steps[*].uses
One or more jobs, including runners, matrices, permissions, or dependenciesReusable workflowA job: jobs.<id>.uses
A small repeated YAML fragment with no meaningful interfaceLeave it inline; an anchor may be enoughNo new component
A result that must block mergingRuleset with a required status checkRepository policy, outside workflow YAML

The important distinction is not file extension. A composite action cannot declare a runner, matrix, job-level permissions, or needs; it executes as steps inside its caller's runner. A reusable workflow owns complete jobs and is called where a job would normally be declared. A ruleset does not run CI at all—it turns a reported check result into a merge constraint.

Part A — extract the deploy summary into a composite action

Create .github/actions/deploy-summary/action.yml. An action directory needs an action.yml metadata file with a name, description, inputs, and runs.using: composite. Every composite run: step also declares its shell because the action, unlike a workflow job, does not own a runner default:

name: Deploy summary
description: Write one deployment report to the run summary

inputs:
  commit-sha:
    description: Commit that produced the deployed artifact
    required: true
  commit-message:
    description: Human-authored commit message
    required: true
  site-directory:
    description: Directory containing the downloaded site
    required: true
  target:
    description: Deployment target shown to the reader
    required: true

runs:
  using: composite
  steps:
    - name: Write deployment summary
      shell: bash
      env:
        COMMIT_SHA: ${{ inputs.commit-sha }}
        COMMIT_MESSAGE: ${{ inputs.commit-message }}
        SITE_DIRECTORY: ${{ inputs.site-directory }}
        DEPLOY_TARGET: ${{ inputs.target }}
      run: |
        FILE_COUNT="$(find "$SITE_DIRECTORY" -type f | wc -l | tr -d ' ')"
        {
          echo "### S3 deploy"
          echo "- **Commit:** $COMMIT_SHA"
          echo "- **Message:** $COMMIT_MESSAGE"
          echo "- **Files:** $FILE_COUNT"
          echo "- **Target:** $DEPLOY_TARGET"
        } >> "$GITHUB_STEP_SUMMARY"

The inputs are the action's interface. The action does not reach into github.event, guess a bucket, or assume dist/; the caller supplies those decisions. The human-authored commit message crosses the same trust boundary as in lesson 4, so it is first assigned to env and then expanded as a quoted shell variable. Expression interpolation never pastes it directly into executable script text.

Use the local action in the deploy job:

      - uses: actions/checkout@v7

      - uses: actions/download-artifact@v8
        with:
          name: site
          path: dist/

      # configure credentials, deploy, and verify as before

      - name: Report deployment
        uses: ./.github/actions/deploy-summary
        with:
          commit-sha: ${{ github.sha }}
          commit-message: ${{ github.event.head_commit.message }}
          site-directory: dist
          target: ${{ env.SITE_URL }}

This checkout is newly necessary. GitHub resolves uses: ./... against files in the job's workspace, and every job starts empty. Put checkout before the local action (and before the artifact download for a predictable clean workspace). A Marketplace action can be downloaded by the runner service; your repository-local action must first exist on disk.

Versioning consequence: ./.github/actions/deploy-summary uses the action from the same checked-out commit as the caller. That gives atomic changes inside one repo, but it is not cross-repository reuse. A shared action would use owner/repo/path@ref; a commit SHA is the strongest immutable ref, at the cost of explicit upgrades.

Part B — lift CI into a reusable workflow

The build and matrix are not one step-shaped unit: they own runners, parallel jobs, a matrix, caches, and the site artifact. Put them in .github/workflows/ci.yml and expose the special workflow_call event:

name: Reusable CI

on:
  workflow_call:

permissions:
  contents: read

jobs:
  build:
    # checkout, Node 24 + npm cache, npm ci, build, upload site

  test:
    # matrix Node 22/24/26, npm cache, npm ci, build

  required:
    name: required
    if: always()
    needs: [build, test]
    runs-on: ubuntu-latest
    steps:
      - name: Require every CI job
        env:
          BUILD_RESULT: ${{ needs.build.result }}
          TEST_RESULT: ${{ needs.test.result }}
        run: |
          test "$BUILD_RESULT" = success
          test "$TEST_RESULT" = success

The event-facing pipeline.yml keeps lifecycle and deployment policy, but replaces its inline build and test jobs with a call:

jobs:
  ci:
    name: ci
    uses: ./.github/workflows/ci.yml

  deploy:
    if: github.event_name == 'push'
    needs: ci
    runs-on: ubuntu-latest
    # existing S3 steps follow

A reusable workflow is called as a job, so the calling job does not also have runs-on or steps. The called jobs still run inside the caller's workflow run. That is why build can upload site and the later caller-side deploy job can download the same artifact—no cross-run transfer was introduced.

The local reusable-workflow path also needs no checkout in the calling job. GitHub loads workflow definitions before runners start, and ./.github/workflows/ci.yml means the file at the caller commit. Checkout is still present inside build and test because those jobs read application files.

Why the extra required job exists

Do not require every matrix check individually. Matrix display names change when supported Node versions change, and a downstream job normally becomes skipped when an upstream job fails. GitHub warns that a skipped dependent job may fail to report the blocking result you intended.

The gate uses if: always(), reads both aggregate job results through needs, and exits nonzero unless both equal success. The check name is stable even if the matrix changes. For a reusable workflow, GitHub formats it as:

<caller job name> / <called job name>

ci / required

Treat that name as a public interface. Renaming caller job ci or called job required without updating the ruleset leaves GitHub waiting for a check that no workflow reports. Required checks do not know about workflow filenames, trigger types, or matrices; they match reported names.

Part C — turn the result into a merge gate

First run the new workflow successfully on a PR so GitHub has observed ci / required. Then create a repository ruleset:

  1. Repository Settings → Rules → Rulesets → New ruleset → New branch ruleset.
  2. Name it protect-main, set enforcement to Active, and target the default branch.
  3. Enable Require a pull request before merging. In a solo playground, keep required approvals at 0; the point today is CI enforcement, not pretending you can independently review yourself.
  4. Enable Require status checks to pass and add the exact check ci / required. Select GitHub Actions as the expected source if the UI offers it.
  5. Enable Require branches to be up to date before merging for strict checking, then create the ruleset without a bypass actor.

Strict mode tests the proposed change against current main; if main advances, the branch must update and CI runs again. That costs more time and Actions minutes than loose mode, but it catches integration failures before merge. A low-risk, high-throughput repository may deliberately choose loose mode. The important part is to make the tradeoff explicit, not inherit a checkbox accidentally.

Avoid a permanent Pending state. Do not add paths: filtering to a workflow that reports a required check: when the whole workflow is filtered out, no result arrives and merging waits forever. A job skipped by an if reports success; an entire required workflow skipped by a filter or skip instruction does not. If you later enable merge queue, add the merge_group trigger so the required check is produced there too.

Exercise 3 — prove the repository rejects red CI

After one green PR run has reported ci / required, create the active protect-main ruleset exactly as described in Part C. Keep the current PR open for the experiment:

  1. temporarily change the build job's npm ci to nmp ci and push;
  2. observe the build failure, the still-executed red ci / required, and the disabled merge path;
  3. restore npm ci, push, and verify the latest SHA turns the required check green;
  4. merge through the PR—do not bypass the rule—and inspect the post-merge deployment.
The deliberate typo cannot merge even though you own the repository. The gate is red rather than skipped. After the fix, strict CI passes on the latest SHA, merge becomes available, and the push run deploys. The final default branch contains no typo and the ruleset remains active.

Design question — decide, then defend

Eight repositories now need the same Node build-and-test policy, but each has a different deployment. A teammate proposes copying ci.yml into all eight repos because a central workflow creates coupling. Choose copying or a shared reusable workflow, state what remains local, and name the tradeoff you accept.

Model answer and rubric

Choose a shared reusable CI workflow pinned by each caller to an immutable commit SHA; keep repository-specific triggers and deployment in each caller. The cohesive shared unit is the build/test policy—Node versions, reproducible install, cache, artifact contract, and stable gate—while deployment targets and credentials vary and should remain local. Copying removes runtime dependency on a central repository but creates eight drifting policy copies; central reuse makes fixes and security policy reviewable in one place. Tradeoff accepted: consumers are coupled to the shared workflow's interface and need an explicit, tested SHA-upgrade process, so central changes do not reach every repo instantly. Full credit for (a) choosing a boundary that matches whole jobs, (b) leaving repo-specific deployment local, and (c) naming either centralized coupling/version rollout cost or copied-policy drift. A composite action alone is incomplete because this reusable unit owns runners, a matrix, jobs, and an artifact.
