Approval-Gated, Keyless Deploys

Lesson 12 · combines planned lessons 15–16 · ~90–120 min · gate production with a human decision, replace stored AWS keys with a short-lived OIDC role, then delete the keys

Prerequisite: lesson 11 complete: CloudFront serves the site over HTTPS, direct S3 reads fail, and the post-merge deploy still authenticates with the temporary IAM-user secrets from lesson 7.

Today you remove two different risks. First, a merge should not silently become a production release: a GitHub Environment will pause the deploy for approval. Second, a credential should not remain valid forever: GitHub OIDC will prove the job's identity to AWS, which returns temporary role credentials.

merge to main │ ▼ GitHub Environment: production ── approval ──► job may start │ ▼ GitHub OIDC token ── aud + exact sub ──► AWS role trust policy │ ▼ temporary AWS role credentials │ ▼ S3 sync → invalidation → live check

Keep the boundaries separate: the Environment authorizes the release; OIDC authenticates the workload; the role's permission policy authorizes AWS operations. Passing one gate does not imply either of the others.

Checkpoint 1 — make production wait

In repository Settings → Environments, create dev and production. Keep dev unprotected for the later PR-preview lesson. On production, allow only the main deployment branch and add a required reviewer. If another trusted person can review the scratch repository, enable Prevent self-review and disable administrator bypass. If you are practicing alone, allow self-review for this exercise and record that this proves the mechanism—not separation of duties.

Store non-secret deployment configuration as production environment variables: AWS_ACCOUNT_ID, AWS_REGION, AWS_ROLE_ARN, S3_BUCKET, CLOUDFRONT_DISTRIBUTION_ID, and CLOUDFRONT_URL. The role does not exist yet, so add its planned ARN now and correct it after creation if necessary.

Add the environment to the existing post-merge deploy job. Do not put it on the reusable CI job: pull requests must still build and test without production approval or AWS identity. 

deploy:
  if: github.event_name == 'push'
  needs: ci
  runs-on: ubuntu-latest
  environment:
    name: production
    url: ${{ vars.CLOUDFRONT_URL }}
  permissions:
    contents: read
  steps:
    # existing deploy steps, still using temporary keys for this checkpoint
Exercise 1 — prove the release gate before changing identity

Write the job edit from scratch, run actionlint, open a small PR, and merge it through ci / required. On the push run, inspect the deployment job before approving it. Confirm that CI completed but no S3 sync or CloudFront invalidation began. Approve the deployment, then confirm the existing key-authenticated deploy succeeds.

The run pauses at production with a review prompt. Approval is recorded in GitHub’s deployment history; only then does the deploy job start and the CloudFront check turn green.
Self-check and failure routing
  • No pause: the job lacks environment: production, the environment name differs by case, or no required reviewer is configured.
  • Approval is impossible: self-review is blocked and no second eligible reviewer exists.
  • PR CI also waits: the environment was attached to ci instead of only deploy.
  • Deploy starts before approval: verify the observed AWS step belongs to the same push run, not an older run.

Checkpoint 2 — define who AWS may trust

In AWS IAM, add one OpenID Connect provider for https://token.actions.githubusercontent.com with audience sts.amazonaws.com. Then create a role named gha-production-deploy. Attach the same narrow S3 and CloudFront permissions already proven by the temporary deploy identity; do not attach AdministratorAccess. The role has two policies with different questions:

Policy Question it answers Required restriction
Trust policy Who may become this role? GitHub provider, AWS audience, exact repository + production environment subject
Permission policy What may the assumed role do? Existing bucket object operations and this distribution’s invalidation only

Get the immutable owner/repository prefix from GitHub rather than guessing numeric IDs: 

gh api repos/{owner}/{repo} \
  --jq '"repo:\(.owner.login)@\(.owner.id)/\(.name)@\(.id):environment:production"'

Use the exact output as the sub. Repositories created before 15 July 2026 may still emit the legacy name-only form unless they opted in; this playground uses the immutable form. An Environment job’s subject ends in environment:production, not ref:refs/heads/main. Branch eligibility belongs in the Environment rule; the AWS trust binds the credential to the protected Environment. 

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::AWS_ACCOUNT_ID:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:OWNER@OWNER_ID/REPO@REPO_ID:environment:production"
        }
      }
    }
  ]
}

Use StringEquals for one exact subject. A wildcard such as repo:ORG/* makes every matching repository a possible credential issuer and defeats the boundary you are building.

Checkpoint 3 — exchange identity, then retire the key

Change only the deploy job’s authentication seam. id-token: write means “allow this job to request an OIDC token”; it does not grant repository writes or AWS permissions. Keep it off the reusable CI job. 

deploy:
  if: github.event_name == 'push'
  needs: ci
  runs-on: ubuntu-latest
  environment:
    name: production
    url: ${{ vars.CLOUDFRONT_URL }}
  permissions:
    contents: read
    id-token: write
  steps:
    - uses: actions/checkout@v7

    - uses: actions/download-artifact@v8
      with:
        name: site
        path: dist/

    - name: Configure temporary AWS credentials
      uses: aws-actions/configure-aws-credentials@v6.2.3
      with:
        role-to-assume: ${{ vars.AWS_ROLE_ARN }}
        aws-region: ${{ vars.AWS_REGION }}
        allowed-account-ids: ${{ vars.AWS_ACCOUNT_ID }}
        role-session-name: gha-${{ github.run_id }}-${{ github.run_attempt }}

    - name: Prove the assumed identity
      run: aws sts get-caller-identity

    # unchanged S3 sync, CloudFront invalidation, live check, and summary

The action asks GitHub for a run-bound token, calls AWS STS AssumeRoleWithWebIdentity, and exports temporary credentials for later AWS CLI steps. allowed-account-ids makes a wrong-account assumption fail immediately. There is no aws-access-key-id or aws-secret-access-key input.

Exercise 2 — prove keyless, then remove the escape hatch
  1. Create the provider and role with the exact trust policy and the existing least-privilege deploy permissions.
  2. Replace the key inputs with the OIDC configuration above; run actionlint.
  3. Merge through green CI, approve production, and inspect get-caller-identity. Its ARN must contain assumed-role/gha-production-deploy/.
  4. Verify the CloudFront URL and direct-S3 denial still pass.
  5. Only after that proof, delete repository secrets AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY, then deactivate and delete the IAM user’s access key. Delete the machine user too if nothing else uses it.
  6. Re-run the same successful push workflow. Approve production again and confirm it stays green without either secret.
Two approved green deployments use the assumed role. The second occurs after both GitHub secrets and the IAM access key are gone. PR CI has no id-token: write, and the live CloudFront site remains correct.
Migration safety checklist
  • Do not delete the old key before one OIDC deployment reaches the live check.
  • If STS says Not authorized to perform sts:AssumeRoleWithWebIdentity, compare the exact aud and immutable Environment sub; do not widen to *.
  • If credentials work but deploy fails, inspect the role permission policy, not its trust policy.
  • If the job never requests a token, confirm id-token: write is on deploy and the credentials step has role-to-assume.
  • If the second run still succeeds after key deletion, that is positive proof only when the workflow has no static-key inputs and the AWS identity is an assumed role.

Check yourself

Design question — decide, then defend

One role or one role per environment?

Your later PR previews need a dev bucket, while production uses the private origin bucket and CloudFront invalidation. Choose (A) one shared deploy role trusted by both environments, or (B) separate dev and production roles. Name the operational cost and the blast-radius consequence.

Model answer and rubric

Choose B: separate roles. The production role trusts only the protected production subject and can write only the production bucket plus invalidate one distribution. The dev role can later trust only dev and write only the preview prefix. A compromised or misconfigured preview job therefore cannot become a production deployment.

The cost is two trust policies, two permission policies, two role ARNs, and coordinated updates when shared deployment needs change. A shared role is simpler, but its permission union lets the least-trusted path inherit the largest blast radius. Full credit requires a decision, that maintenance tradeoff, and a concrete statement about which resources each identity can reach.

Done means zero long-lived AWS deploy credentials. Disabling or ignoring the old GitHub secrets is not retirement; delete the secrets and the IAM access key after the OIDC proof.

Ask your teacher if approval never appears, no eligible reviewer can approve, the Environment subject differs from the trust policy, STS rejects role assumption, or the assumed role lacks one deploy permission. Bring the job’s Environment name, exact redacted aud/sub, role ARN, and first AWS error. Do not fix trust failures with wildcards.
