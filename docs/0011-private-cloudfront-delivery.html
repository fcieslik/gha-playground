The public S3 website was a useful proof of the deploy loop, not a production boundary. Anyone can bypass it, it is HTTP-only, and its public-read policy is the opposite of an origin that only your delivery layer may read. Today you replace it with a deliberately small architecture: CloudFront is the public HTTPS entry point; a private S3 bucket is the origin; Origin Access Control (OAC) is the one identity allowed to read it.

Course connection: revisit Frontend Masters’ Deploying to AWS segment. For the current implementation details, use AWS’s OAC and private S3 origins guide, then keep the S3 PoC reference open only for the existing deploy identity and teardown commands.

See the boundary before changing it

Before: viewer ──HTTP──> public S3 website endpoint ▲ ▲ └── can bypass ┘ After: viewer ──HTTPS──> CloudFront distribution ──signed HTTPS──> private S3 bucket public entry point ▲ │ bucket policy allows only CloudFront service principal when AWS:SourceArn == this distribution ARN

The crucial vocabulary is origin, not “website.” CloudFront must use the bucket’s normal S3 REST origin, such as BUCKET.s3.REGION.amazonaws.com. The S3 website endpoint is a custom origin and cannot use OAC. Set the CloudFront default root object to index.html; do not leave static website hosting as a dependency.

# ADR-002: Deliver the static site through CloudFront with a private S3 origin

## Status
Accepted — 2026-07-24

## Context
The public S3 website endpoint proves deployment but has no HTTPS and lets
viewers bypass any edge policy. We need one public HTTPS entry point while
keeping the tested site artifact and the existing least-privilege deploy
identity. Edge caching reduces latency and origin requests, but makes a
new or rolled-back object temporarily less immediately visible.

## Decision
We will serve the site through a CloudFront distribution with HTTPS redirect,
an S3 REST origin, and an OAC that always signs origin requests. The bucket
will block public access and allow s3:GetObject only to CloudFront when the
request SourceArn is this distribution. The default root object is index.html.

## Consequences
- Direct S3 object URLs are denied; the CloudFront domain is the only public
  delivery entry point.
- We retain the current artifact-to-S3 deploy contract and verify the
  CloudFront URL after deployment.
- We accept propagation and caching delay. A release or rollback may need a
  targeted invalidation until immutable, content-hashed asset names exist.
- CloudFront adds a billable service and a second operational configuration.

Implement the accepted boundary

Create one standard CloudFront distribution. Choose the existing bucket as an S3 bucket origin—not its website endpoint—then set Viewer protocol policy to Redirect HTTP to HTTPS, Allowed HTTP methods to GET, HEAD, and Default root object to index.html. Create an OAC for origin type S3 with Sign requests (recommended), attach it to that origin, and wait until the distribution status is Deployed.

OAC’s “always sign” setting means CloudFront signs requests it sends to the S3 origin. It does not grant access on its own; the bucket policy is the second half. Keep S3 Block Public Access enabled and replace the old public-read statement with this narrowly scoped read permission:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCloudFrontReadOnly",
      "Effect": "Allow",
      "Principal": { "Service": "cloudfront.amazonaws.com" },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::YOUR-ACCOUNT-ID:distribution/YOUR-DISTRIBUTION-ID"
        }
      }
    }
  ]
}

The condition is not decoration. The CloudFront service principal is broad; AWS:SourceArn narrows it to the one distribution you control. Your Actions IAM user still has its separate PutObject/DeleteObject deploy authority from lesson 7. Do not add write authority for CloudFront; viewers only read this static origin.

Cache is release behavior

A cache hit is a copy at an edge, not proof that the origin has the latest object. For this un-hashed starter site, choose a simple, explicit release policy: use the managed CachingOptimized cache policy for the default behavior and invalidate /* after every deploy. That is intentionally correct-before-cheap. Lesson 14 replaces blanket invalidation with cache headers and immutable hashed asset names.

Do not confuse invalidation with deployment. aws s3 sync --delete converges origin objects to the artifact; an invalidation tells CloudFront not to keep serving cached copies. They solve separate states. Invalidation paths beginning with / match the viewer URL path, so /* is the broad, easy-to-reason-about first policy.

Exercise 2 — cut over without widening access

After ADR-002 is committed, create the distribution and OAC as above. Replace—not append to—the bucket’s old public-read policy. Keep Block Public Access on. Once the CloudFront check is green, disable S3 static website hosting: the website endpoint is no longer part of the system. Record the CloudFront domain as CLOUDFRONT_URL in pipeline.yml, then change the deploy job’s final live check to:

- run: curl --fail --silent --show-error "$CLOUDFRONT_URL" | grep --fixed-strings "Deployed by GitHub Actions"

Open a small PR and merge through the existing ruleset. On the post-merge run, deploy the same site artifact, invalidate /*, then run the CloudFront curl check. The invalidation command needs the distribution ID and caller reference, which must be unique per request:

aws cloudfront create-invalidation \
  --distribution-id "$CLOUDFRONT_DISTRIBUTION_ID" \
  --paths '/*' \
  --caller-reference "$GITHUB_RUN_ID-$GITHUB_RUN_ATTEMPT"
The CloudFront HTTPS URL returns the expected phrase. The direct object URL such as https://BUCKET.s3.REGION.amazonaws.com/index.html returns 403 AccessDenied. The Actions run still uploads only the site artifact; it has not rebuilt the site or given CloudFront write access.
Cutover checklist
  1. Distribution origin is the normal bucket REST origin; Default root object is index.html.
  2. Viewer policy redirects HTTP to HTTPS; OAC is S3 type with Sign requests enabled.
  3. Bucket Block Public Access remains enabled; no Principal: "*" allow statement remains.
  4. After the CloudFront check is green, S3 static website hosting is disabled.
  5. Bucket policy principal is cloudfront.amazonaws.com and its SourceArn contains the exact account and distribution IDs.
  6. pipeline.yml verifies the CloudFront URL after sync and invalidation; the old S3 website endpoint is removed from the health check too.
  7. Direct S3 returns 403; CloudFront returns 200 and the expected phrase.

If CloudFront returns 403, first check the origin is not the website endpoint, the distribution has fully deployed, and the policy's distribution ID/account ID exactly match. Do not “fix” it by reopening public read.

Design question — decide, then defend

Your site now has an un-hashed app.js whose contents change on every release. Choose one release policy for now: (A) one-year cache TTL with a /* invalidation on each deploy, or (B) a five-minute TTL and no invalidations. State which failure users can see after a release or rollback, and name the cost you accept.

Model answer and rubric

Choose A for this small, release-driven site. A long TTL keeps repeat reads fast and inexpensive, while the deployment invalidation makes the new or restored release visible promptly. The accepted costs are invalidation operations, propagation delay while the invalidation completes, and a pipeline step that can fail separately from S3 sync. Without a completed invalidation, users may receive the cached prior version.

B is defensible when minimizing release operations matters more than prompt freshness, but after a release or rollback users can receive the prior app.js for up to five minutes. Its accepted cost is bounded staleness and more origin/cache-miss traffic. Full credit requires a choice, the stale-content failure mode, and a concrete latency/cost/operational tradeoff. The long-term improvement is content-hashed asset names with long immutable caching; that is deliberately deferred until release hardening.

Bring the exact origin domain, CloudFront distribution ID, bucket-policy statement, HTTP status from both URLs, and invalidation status if the cutover fails. Do not resolve a 403 by making the bucket public.
